### Multi-phase or multi-PR plan

The plan is the deliverable. Do not implement it.

1. Skip planning for an obvious one-file change. State why.
2. Settle observable design questions with a prototype. Reserve human questions for product, preference, release, or authority calls.
3. Ground the affected systems with `how`, broad fresh `scout` retrieval, and `why` when history constrains the design.
4. Write one ordered section per independently verifiable unit. Each section names dependencies, files, exact behavior, owner, acceptance checks, live verification, risks, and rollback.
5. Name one writer per checkout or an isolated worktree. Every worker receives a standalone brief. Reviews use fresh `reviewer` runs.
6. For a standing program, route execution to Orchestrate. For one long predicate-driven task, route to Autonomous run.
7. Discover an installed Pi verification tool for each product surface. If none exists, mark live verification unavailable and name the missing capability. Do not replace it with a proxy claim.
8. Run `technical-writing`, `unslop`, and any project plan checker. Hand back the plan path and checker output, then stop.

Every unit ends with direct evidence against the real artifact. Tests alone do not prove a user-facing path.
